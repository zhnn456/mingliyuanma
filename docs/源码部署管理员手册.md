## 1. 业务模型与角色

### 1.1 源码部署业务定位

源码部署是平台的**一次性买断**产品线，与 SaaS 分站互补：

| 维度 | SaaS 分站 | 源码部署 |
|------|-----------|----------|
| 交付物 | 主站子账号 | 完整源码包 + 授权码 |
| 服务器 | 平台提供 | 客户自备 |
| 数据库 | 平台共享 | 客户独立 |
| 收入归属 | 平台收，分润给代理 | 客户独享 |
| 授权方式 | 订阅制 | 永久授权 + 1年免费升级 |
| 依赖平台 | 持续依赖 | 仅升级检查时联系 |

### 1.2 关键技术资产

| 资产 | 位置 | 作用 |
|------|------|------|
| 授权码生成器 | `src/lib/license-generator.ts` | HMAC-SHA256 签名，生成不可伪造的授权码 |
| 升级 token 管理 | `src/lib/upgrade-tokens.ts` | 内存级 token，绑定 IP，2小时过期，一次性使用 |
| 升级检查接口 | `src/app/api/upgrade/check/route.ts` | 验证授权码 + 升级权益，返回下载 token |
| 升级下载接口 | `src/app/api/upgrade/download/route.ts` | 验证 token，返回更新包文件流 |
| 续费接口 | `src/app/api/admin/upgrade/renew/route.ts` | 管理员延长客户升级权益 |
| 客户升级脚本 | `deploy/update.sh` | 客户服务器上一键检查+下载+备份+部署 |
| 代码混淆 | `next.config.js` | 生产构建混淆，保护前端逻辑 |
| 中央密钥 | `CENTER_SECRET_KEY` 环境变量 | 授权码签名密钥，仅中央服务器持有 |

### 1.3 数据库表结构

| 表 | 关键字段 | 说明 |
|------|------|------|
| `Agent` | `licenseKey`, `level`, `domain`, `upgradePlan`, `upgradeExpiryAt` | 代理商记录，level='source' 为源码客户 |
| `UpgradePackage` | `version`, `minVersion`, `filePath`, `checksum`, `status` | 升级包记录 |
| `UpgradeDownloadLog` | `agentId`, `version`, `clientIP`, `downloadToken`, `status` | 下载日志（check/downloaded） |

## 2. 源码客户全生命周期

```
客户咨询 → 签约付费 → 生成授权码 → 构建交付包 → 交付部署
    │                                        │
    │                                        ↓
    │                                    客户上线运营
    │                                        │
    ↓                                        ↓
 1年免费升级期 ────到期────→ 续费决策 ──是→ 年度升级服务（¥1000/年）
    │                                        │
    否                                       ↓
    ↓                                    持续更新
 不续费：系统正常用，无新版本更新
```

### 2.1 各阶段管理员职责

| 阶段 | 管理员操作 | 涉及系统功能 |
|------|-----------|-------------|
| 签约 | 记录客户域名、联系人 | — |
| 开通 | 创建 Agent（level=source）+ 生成授权码 | 管理后台 → 代理商管理 |
| 交付 | 构建源码包 + 填写 .env 模板 | `npm run build` |
| 升级权益 | 设置 upgradePlan=free, upgradeExpiryAt=+1年 | 数据库 / 续费接口 |
| 发版 | 发布 UpgradePackage 记录 | 管理后台 → 版本发布 |
| 续费 | 调用续费接口延长 upgradeExpiryAt | `/api/admin/upgrade/renew` |
| 停用 | 冻结授权码 / 暂停代理商 | 管理后台 → 授权码管理 |

## 3. 授权码体系

### 3.1 授权码结构

授权码格式：`LIC.<base64url(payload)>.<hmac_signature>`

**payload 字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `agentId` | string | 代理商 ID |
| `features` | string[] | 功能模块（bazi/ziwei/qimen/meihua/offering） |
| `maxUsers` | number | 最大用户数 |
| `issuedAt` | number | 签发时间戳 |
| `expiryAt` | number\|null | 过期时间（源码买断=null 永久） |
| `version` | number | 授权码版本号（当前=2） |
| `domain` | string | 绑定域名 |
| `level` | string | 授权等级（source=源码买断） |
| `monthlyFee` | number | 月费（源码=0） |
| `upgradeExpiryAt` | number\|null | 升级服务到期时间戳 |
| `upgradePlan` | string | 升级方案（free/annual/none） |

### 3.2 签名机制

- 算法：HMAC-SHA256（Node.js 原生 `crypto.createHmac`）
- 密钥：`CENTER_SECRET_KEY` 环境变量
- 验证：常量时间比较（`timingSafeEqual`），防时序攻击
- 编码：Base64URL（URL 安全，无 padding）

> ⚠️ **关键**：授权码生成与验证必须使用相同的 `CENTER_SECRET_KEY`。中央服务器和客户服务器（仅验证时通过 API）共享此密钥。密钥泄露将导致授权体系崩溃。

### 3.3 域名绑定

授权码绑定域名，客户服务器 middleware 校验：
- 请求域名 ≠ 授权域名 → 返回 403 `DOMAIN_MISMATCH`
- 换域名需重新生成授权码（见[第9节](#9-域名变更流程)）

### 3.4 生成授权码

**方式一：管理后台**（推荐）

管理后台 → 代理商管理 → 创建代理商 → 选择"源码部署" → 系统自动生成授权码

**方式二：脚本生成**（用于测试）

```bash
# 在服务器上执行测试脚本
cd /www/ming8 && node scripts/test-upgrade-flow.mjs
```

测试脚本会生成一个测试授权码，绑定 `test-deploy.example.com`，升级方案 `free`，有效期 1 年。

## 4. 升级权益管控

### 4.1 三种升级方案

| 方案 | upgradePlan | 含义 | 价格 |
|------|------------|------|------|
| 免费1年 | `free` | 购买后1年内免费升级 | ¥0（含在买断价） |
| 年度付费 | `annual` | 续费后1年升级服务 | ¥1,000/年 |
| 无权益 | `none` | 不续费，系统正常用但无新版本 | ¥0 |

### 4.2 字段控制逻辑

```
upgradePlan === 'none' 或 upgradeExpiryAt === null
    → 拒绝升级（"升级服务未激活"）

upgradeExpiryAt < now
    → 拒绝升级（"升级服务已于 X 到期"）

否则
    → 允许升级，生成下载 token
```

### 4.3 数据库字段

```sql
-- Agent 表升级权益字段
ALTER TABLE Agent ADD COLUMN upgradePlan VARCHAR(20) DEFAULT 'none';
ALTER TABLE Agent ADD COLUMN upgradeExpiryAt DATETIME NULL;
```

迁移脚本：`scripts/mysql-migrate-v4.1.0.sql`（可安全重复执行）

### 4.4 权益配置示例

```sql
-- 新源码客户：免费1年升级
UPDATE Agent
SET upgradePlan = 'free',
    upgradeExpiryAt = DATE_ADD(NOW(), INTERVAL 1 YEAR)
WHERE id = 'agt_xxx';

-- 续费客户：年度付费
UPDATE Agent
SET upgradePlan = 'annual',
    upgradeExpiryAt = DATE_ADD(NOW(), INTERVAL 1 YEAR)
WHERE id = 'agt_xxx';

-- 不续费：降级
UPDATE Agent
SET upgradePlan = 'none',
    upgradeExpiryAt = NULL
WHERE id = 'agt_xxx';
```

## 5. 升级包发布流程

### 5.1 发布升级包

**步骤：**

1. 本地完成版本开发，更新版本号
2. 构建：`npm run build`
3. 打包升级内容（变化的文件）
4. 上传到服务器 `/www/ming8/updates/v<版本>/update-v<版本>.zip`
5. 计算校验值：`md5sum update-v<版本>.zip`
6. 插入 UpgradePackage 记录：

```sql
INSERT INTO UpgradePackage
  (id, version, minVersion, filePath, fileSize, checksum, changelog, requiresMigration, status, publishedAt, createdAt, updatedAt)
VALUES
  ('pkg-v4.1.0', 'v4.1.0', 'v4.0.0', '/www/ming8/updates/v4.1.0/update-v4.1.0.zip',
   107, 'e27c9e5622f9ef5231ad591fa95defb9',
   '1. 新增功能A\n2. 修复问题B\n3. 优化性能C',
   0, 'published', NOW(), NOW(), NOW());
```

### 5.2 字段说明

| 字段 | 说明 |
|------|------|
| `version` | 新版本号（如 v4.1.0） |
| `minVersion` | 最低要求版本（低于此版本需先升级到中间版本） |
| `filePath` | 服务器上升级包的绝对路径 |
| `fileSize` | 文件大小（字节） |
| `checksum` | MD5 校验值 |
| `changelog` | 更新日志 |
| `requiresMigration` | 是否需要数据库迁移（1=需要） |
| `status` | 状态（published=已发布） |

### 5.3 版本号规则

采用语义化版本：`主版本.次版本.修订号`

| 变化 | 含义 | 示例 |
|------|------|------|
| 主版本 (X.0.0) | 架构大改，需手动适配 | v4.0.0 → v5.0.0 |
| 次版本 (X.Y.0) | 新增功能，向下兼容 | v4.0.0 → v4.1.0 |
| 修订号 (X.Y.Z) | Bug 修复，完全兼容 | v4.0.0 → v4.0.1 |

## 6. 升级检查与下载接口

### 6.1 升级检查接口

**接口：** `GET /api/upgrade/check`

**参数：**

| 参数 | 说明 |
|------|------|
| `license` | 完整授权码 |
| `domain` | 客户域名 |
| `currentVersion` | 客户当前版本 |

**处理流程：**

```
1. 验证授权码签名（HMAC-SHA256）
   失败 → 403 "授权码无效"

2. 查询 Agent 记录
   不存在 → 403 "代理商记录不存在"

3. 检查升级权益（upgradePlan / upgradeExpiryAt）
   无权益 → 403 "升级服务未激活"
   已过期 → 403 "升级服务已于 X 到期"

4. 查询最新 UpgradePackage（status=published）

5. 版本比较
   当前版本 ≥ 最新版本 → "已是最新版本"
   当前版本 < minVersion → "需先升级到 X 以上版本"

6. 生成下载 token（2小时有效，绑定 IP）

7. 记录检查日志（UpgradeDownloadLog，status=check）

8. 返回下载地址 + token + 版本信息
```

**成功响应：**

```json
{
  "hasUpdate": true,
  "latestVersion": "v4.1.0",
  "currentVersion": "v4.0.0",
  "changelog": "1. 新增功能A\n2. 修复问题B",
  "requiresMigration": false,
  "downloadUrl": "https://ming8.online/api/upgrade/download?token=xxx",
  "downloadToken": "xxx",
  "fileSize": 107,
  "checksum": "e27c9e5622f9ef5231ad591fa95defb9",
  "upgradePlan": "free",
  "upgradeExpiryAt": "2027-08-16T06:15:19.000Z"
}
```

### 6.2 下载接口

**接口：** `GET /api/upgrade/download?token=xxx`

**处理流程：**

```
1. 验证 token（存在性 + 过期检查）
   无效 → 403 "下载令牌无效或已过期"

2. 检查 IP 绑定
   不匹配 → 403 "下载令牌与请求 IP 不匹配"

3. 查询 UpgradePackage

4. 验证文件存在

5. 一次性使用（下载后删除 token）

6. 记录下载日志（status=downloaded）

7. 返回文件流（Content-Type: application/zip）
```

### 6.3 token 安全机制

| 特性 | 说明 |
|------|------|
| 长度 | 32 字节随机 hex（64 字符） |
| 有效期 | 2 小时 |
| IP 绑定 | check 时的客户端 IP 必须与 download 时一致 |
| 一次性 | 下载成功后立即删除 |
| 存储 | 内存（`Map`），进程重启失效 |

## 7. 客户侧一键升级

### 7.1 升级脚本

客户服务器上的 `deploy/update.sh` 自动完成：

```
Step 1: 检查更新（调用 /api/upgrade/check）
Step 2: 下载更新包（用 token 调用 /api/upgrade/download）
Step 3: 备份当前版本（backup-yyyyMMdd 目录）
Step 4: 解压新版本
Step 5: 保留 .env 配置和数据库
Step 6: 安装依赖（如有变化）
Step 7: 执行数据库迁移（如有）
Step 8: 重新构建 + 重启 PM2
```

### 7.2 客户配置

客户 `.env` 中必须配置：

```bash
APP_LICENSE_KEY=LIC.xxx       # 授权码
NEXTAUTH_URL=https://客户域名   # 绑定域名
CENTER_API=https://ming8.online # 中央服务器
```

### 7.3 执行升级

```bash
cd /www/mingliyuanma
bash deploy/update.sh
```

## 9. 域名变更流程

当客户需要更换部署域名时：

1. **验证新域名**：确认客户对新域名有控制权
2. **重新生成授权码**：绑定新域名
3. **更新数据库**：

```sql
UPDATE Agent
SET domain = '新域名.com',
    licenseKey = '新授权码'
WHERE id = 'agt_xxx';
```

4. **交付新授权码**给客户
5. **客户更新** `.env` 中的 `APP_LICENSE_KEY` 和 `NEXTAUTH_URL`
6. **重启服务**：`pm2 restart ming8`

**费用：** 首次免费，之后 ¥100/次。

### 10.2 权限设计

- 顶部橙色横幅提示"演示体验模式"
- MutationObserver 监听 DOM，写操作按钮（识别文案关键词）置灰 + 加锁图标 + 禁用点击
- hover 显示"演示账号无权操作"

## 11. 交付清单与版本管理

### 11.1 交付给客户的内容

| 文件 | 说明 | 来源 |
|------|------|------|
| 源码包 | `.next/standalone` 构建产物 | `npm run build` |
| `.env.example` | 环境变量模板 | 项目根目录 |
| `ecosystem.config.js` | PM2 配置 | `deploy/` |
| `update.sh` | 一键升级脚本 | `deploy/` |
| 授权码 | HMAC 签名授权码 | 管理后台生成 |
| 交付指南 | 部署文档 | `docs/源码部署交付指南.md` |

### 11.2 交付方式

- **GitHub 私有仓库**（推荐）：邀请客户协作，可接收后续更新
- **压缩包**：一次性交付，后续通过升级接口更新

### 11.3 代码保护

| 层 | 机制 | 说明 |
|---|------|------|
| 1 | 服务端逻辑 | 核心算法在 API 路由，前端无法获取 |
| 2 | 前端混淆 | 生产构建时自动混淆，变量名十六进制化 |
| 3 | 域名绑定 | middleware 校验，换域名 403 |
| 4 | 在线验证 | 10分钟向主站验证授权状态 |
| 5 | 授权过期锁定 | 过期后全站锁定 |
| 6 | HMAC 签名 | 授权码不可伪造 |
| 7 | 编译保护 | 部署后是编译产物，非原始源码 |

> **注意**：GitHub 上的源码始终是明文（正常现象）。混淆在 `npm run build` 时生效，部署到服务器后浏览器访问的是混淆后的代码。客户获得的是编译后的生产包，不含原始源码。

## 13. 故障排查

### 13.1 授权码签名验证失败

**现象：** check 接口返回 403 "授权码无效"

**排查：**

```bash
# 1. 检查 CENTER_SECRET_KEY 是否一致
grep CENTER_SECRET_KEY /www/ming8/.env

# 2. 重新生成授权码测试
cd /www/ming8 && node scripts/test-upgrade-flow.mjs

# 3. 检查授权码格式（LIC. 开头，三段式）
```

**常见原因：**
- 中央服务器与生成端 `CENTER_SECRET_KEY` 不一致
- 授权码被截断（URL 编码问题）
- 使用了旧的 `crypto.subtle` 实现（已修复为 `crypto.createHmac`）

### 13.2 版本检查"版本过低"

**现象：** 返回"当前版本 vX 过低，需先升级到 vY 以上版本"

**原因：** 当前版本低于升级包的 `minVersion`

**解决：**
- 客户需先升级到中间版本
- 或调低 `UpgradePackage.minVersion`

### 13.3 下载"IP 不匹配"

**现象：** download 接口返回 403 "下载令牌与请求 IP 不匹配"

**原因：** check 和 download 两次请求的客户端 IP 不一致

**解决：**
- 真实场景：客户服务器有多个出口 IP 时，需统一出口
- 测试场景：测试脚本需给两次请求带相同的 `x-forwarded-for` 头

### 13.4 demo 账号无法登录后台

**排查：**

```bash
# 1. 确认账号存在且角色正确
mysql -u ming8 -p ming8_db -e \
  "SELECT email, role FROM User WHERE email='demo@ming8.online'"

# 2. 确认 middleware 已部署最新版本
# 3. 确认 requireAdmin 已放行 demo
```

### 13.5 升级包文件不存在

```bash
# 检查文件
ls -la /www/ming8/updates/v4.1.0/update-v4.1.0.zip

# 检查数据库记录
mysql -u ming8 -p ming8_db -e \
  "SELECT version, filePath, status FROM UpgradePackage WHERE version='v4.1.0'"
```

## 15. 安全规范

### 15.1 密钥管理

| 密钥 | 用途 | 存储位置 | 泄露影响 |
|------|------|----------|----------|
| `CENTER_SECRET_KEY` | 授权码签名 | `.env` | 授权体系崩溃 |
| `NEXTAUTH_SECRET` | Session 签名 | `.env` | 会话伪造 |
| `MYSQL_PASSWORD` | 数据库 | `.env` | 数据泄露 |

**要求：**
- 密钥长度 ≥ 32 字节
- 定期轮换（建议每季度）
- 不提交到 Git 仓库
- 不在聊天/邮件中传输明文

### 15.2 演示账号安全

- demo 账号仅限查看，写操作双重锁定（前端 + 后端）
- 定期更换 demo 密码
- 监控 demo 账号异常访问
- demo 账号不能调用任何写接口

### 15.3 升级包安全

- 升级包文件校验值（MD5）必须记录
- 下载 token 一次性使用，2小时过期
- 下载绑定 IP，防 token 盗用
- 升级包文件路径不可外泄

### 15.4 违约处理

| 违规行为 | 处理方式 |
|----------|----------|
| 私自伪造授权码 | 立即吊销，追究法律责任 |
| 二次倒卖源码 | 立即吊销，追究法律责任 |
| 换域名未报备 | 冻结授权，补办后恢复 |
| 授权过期继续用升级 | 升级接口自动拒绝 |
