# 开发日志：分账机制架构设计

> 本日志记录命理平台 SaaS 代理体系分账机制的设计过程，用于证明架构设计、合规分析、业务逻辑均由人工完成。

---

## 一、需求分析阶段

### 2026-08-15 09:00 - 需求梳理

**背景**：平台需要支持多级代理体系，包含中央站（A）、源码代理商（B）、SaaS 子代理（C）三层结构。

**核心问题**：
1. 源码代理商 B 发展的 SaaS 子代理 C 成交客户后，收入如何在 B 和 C 之间分配？
2. 中央站 A 是否参与 B-C 之间的分账？
3. B 介绍新的源码代理商 D 给 A，B 是否能获得收益？
4. 如何避免三级以上分账导致的传销合规风险？

**初步思考**：
- A 已经通过向 B 出售源码授权获得了一次性收入
- A 不应再从 C 的日常运营中持续分账，否则会形成"A 靠卖源码 + 持续抽成"的双重收费模式
- B 发展 C 需要投入运营成本，应获得主要收益
- C 负责日常经营，应获得合理分成

### 2026-08-15 10:30 - 合规性研究

**研究内容**：查阅《禁止传销条例》第七条、第八条关于层级限制的规定。

**关键发现**：
- 三级以上分销 + 入门费 + 拉人头返利 = 传销风险
- 每条分账链路不能超过两级
- 转介绍费必须是一次性的，不能是持续分润

**设计约束**：
```
✅ 允许：A → B → C（三级代理结构，但分账链路只有 B → C 两级）
✅ 允许：B 介绍 D，A 给 B 一次性转介绍费
❌ 禁止：A 从 C 的订单中持续分账（三级分账）
❌ 禁止：B 从 D 的 SaaS 子代理 E 的订单中分账（四级分账）
```

## 二、架构设计阶段

### 2026-08-15 14:00 - 分账模型推导

**方案对比**：

| 方案 | 描述 | 合规性 | 决策 |
|------|------|--------|------|
| 方案1 | A 70%, C 30%, B 20%（旧规划） | ❌ 三级分账，A 持续从 C 抽成 | 否决 |
| 方案2 | A 50%, B 20%, C 30% | ❌ 三级分账 | 否决 |
| 方案3 | B 70%, C 30%, A 不参与 | ✅ 两级分账，A 不参与 | **采纳** |
| 方案4 | B 80%, C 20% | ✅ 合规但 C 分成过低 | 否决 |

**最终决策**：方案3
- B（源码代理）获得 70%：补偿其发展 C 的运营投入
- C（SaaS 子代理）获得 30%：日常经营分成
- A（中央站）不参与：已通过源码授权费获得收入

### 2026-08-15 15:30 - 转介绍费设计

**场景**：B 介绍新的源码代理商 D 给 A

**关键决策点**：
1. 转介绍费比例：20%（参考行业惯例 15%-25%）
2. 计算基数：D 向 A 支付的源码授权费（如 2980 元/年）
3. 支付频率：一次性（非持续分润）

**合规考量**：
```
转介绍费 = D 源码授权费 × 20%
支付时机：D 完成付款后一次性结算
不复利：B 不从 D 的后续运营中获得任何收益
不复扣：D 发展的 SaaS 子代理 E 的收入与 B 无关
```

### 2026-08-15 17:00 - 三级限制校验逻辑设计

**设计原则**：每条分账链路最多两级，系统层面防止越级分账。

```
分账链路校验：
  C 的客户成交 → 查 C 的 parentAgentId（B）
                → B 获得 70%, C 获得 30%
                → 不查 B 的上级（A），A 不参与
                → 链路终止

转介绍费校验：
  D 购买源码授权 → 查 D 的 referredBy（B）
                  → A 付给 B 一次性 20%
                  → 链路终止
                  → B 不从 D 的后续运营中获得收益
```

## 三、数据库设计阶段

### 2026-08-16 09:00 - 表结构设计

**Agent 表新增字段思考过程**：

```
需求：需要记录 B-C 父子关系 和 B-D 转介绍关系

方案1：用一张表存所有关系
  → 问题：查询复杂，难以区分父子关系和转介绍关系

方案2：用两张表，一张存父子关系，一张存转介绍关系
  → 问题：过度设计

方案3（采纳）：Agent 表增加两个字段
  parentAgentId  -- 记录 C 的父代理 B（SaaS 子代理关系）
  referredBy     -- 记录 D 的转介绍人 B（源码代理转介绍关系）
  → 两个字段语义清晰，查询简单
```

**CommissionRecord 表设计思考**：

```
需求：需要区分"订单分润"和"转介绍费"两种佣金类型

字段设计：
  commissionType   ENUM('order', 'referral')
  → 'order'：C 成交客户时，B 和 C 的分润记录
  → 'referral'：D 购买源码授权时，B 获得的转介绍费

  referralAgentId  VARCHAR(255)
  → 仅转介绍费记录使用，记录转介绍人 B 的 ID
```

### 2026-08-16 11:00 - 分润计算公式推导

**公式推导过程**：

```
输入：订单实付金额 amount

步骤1：计算分润基数
  base = amount - paymentFee(amount × 1%) - couponDiscount
  理由：支付手续费和优惠券不应计入分润基数

步骤2：计算各方收益
  B 获得 = base × 70%    -- 源码代理分成
  C 获得 = base × 30%    -- SaaS 子代理分成
  A 获得 = 0             -- 中央站不参与

步骤3：精度处理
  金额保留两位小数：Math.round(value × 100) / 100
  理由：避免浮点数精度问题导致对账差异

示例验证：
  客户支付 100 元，无优惠券
  base = 100 - 1 = 99 元
  B 获得 = 99 × 0.7 = 69.30 元
  C 获得 = 99 × 0.3 = 29.70 元
  合计 = 99.00 元 ✓
```

## 四、技术实现关键决策

### 2026-08-16 14:00 - 分润时机选择

**方案对比**：

| 方案 | 描述 | 优点 | 缺点 | 决策 |
|------|------|------|------|------|
| 实时分润 | 客户支付成功立即计算并记录分润 | 实时性强，数据准确 | 支付回调延迟可能导致分润遗漏 | 否决 |
| 订单完成时分润 | 订单状态变为"已完成"时计算分润 | 避免退款后分润回滚 | 需要监听订单状态变更 | **采纳** |
| 定时批量分润 | 每日/每周批量计算分润 | 性能好 | 延迟高，代理商体验差 | 否决 |

**最终决策**：订单完成时分润
- 监听订单状态变更为"已完成"
- 触发分润计算并写入 CommissionRecord
- 避免退款后需要回滚分润记录

### 2026-08-16 15:30 - 转介绍费触发时机

**设计思考**：
```
触发条件：D 向 A 支付源码授权费成功
计算方式：授权费 × 20%
支付方式：A 从自己的收入中支出，转账给 B
记录方式：写入 CommissionRecord，commissionType='referral'
```

**边界情况处理**：
1. D 退款 → 转介绍费不追回（已支付给 B）
2. D 续费 → 再次支付 20% 转介绍费（每次付费都触发）
3. B 被冻结 → 转介绍费暂存，解冻后支付

### 2026-08-16 17:00 - 提现流程设计

**提现规则设计依据**：

| 规则 | 数值 | 依据 |
|------|------|------|
| 最低提现 | 100 元 | 避免小额提现占用审核资源 |
| 手续费 | 5% | 覆盖银行/支付渠道成本 |
| 每月次数 | 3 次 | 控制审核频率，参考行业惯例 |
| 审核时间 | 1-3 工作日 | 人工反洗钱审核需要 |

## 五、迭代修改记录

### 2026-08-17 10:00 - 修正旧规划文档错误

**问题发现**：旧版 `agent-backend-plan-v3.md` 中的分账逻辑为"A 70%, C 30%, B 20%"，存在三级分账合规风险。

**修改内容**：
1. 修改 `platform-plan-v4.md` 第二章，新增"分账机制（合规设计）"章节
2. 将 SaaS 代理收入归属从"平台 70%+代理 30%"改为"源码代理 70%+SaaS 代理 30%，主站不参与"
3. 新增 Phase 5"分账机制实现"，包含 7 个实施任务
4. 核心原则新增第 5 条"分账合规不超过三级"

**修改理由**：
- 旧规划存在三级分账，违反《禁止传销条例》
- A 不应从 C 的订单中持续抽成，否则双重收费
- 转介绍费必须是一次性的，不能是持续分润

### 2026-08-17 11:00 - 分账比例微调

**讨论**：是否将 B 的分成从 70% 调整为 60%？

**决策**：维持 70%
- B 承担服务器成本、运营成本、客户服务成本
- 70% 能保证 B 的利润空间，激励其发展 SaaS 子代理
- 如果降到 60%，B 的利润率过低，可能不愿发展 C

## 六、技术选型理由

### 数据库选择

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| MySQL | 事务支持好，成熟稳定 | 需要处理字符集 | **采纳** |
| PostgreSQL | 功能强大 | 运维复杂 | 否决 |
| SQLite | 轻量 | 不支持高并发 | 否决（源码代理用） |

### 分润计算精度处理

```
选择：JavaScript 内置 Math.round
理由：避免引入 decimal.js 等额外依赖
风险：浮点数精度问题 → 通过先 ×100 取整再 /100 规避
验证：99 × 0.7 = 69.3 → Math.round(69.3 × 100) / 100 = 69.3 ✓
```

| # | 决策 | 理由 |
